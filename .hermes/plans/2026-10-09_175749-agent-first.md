# Xenia agent-first module layer — implementation plan

Goal: make a small, locally usable, repository-only composition layer over existing Xenia functions, with explicit module lifecycle and a removable AgentTool integration.

Architecture: a zero-dependency in-process registry owns admission and lifecycle for trusted module implementations. It does not become a model harness, permission authority, package installer, or replacement for Surface, Covenant or Work. Existing functions supply the actual behavior. An optional adapter uses the public AgentTool local-starter preview and a host-selected notes root; retained data stays outside code and survives retirement.

Tech stack: Node >=22 ESM, built-in node:test; existing Xenia build and Ajv dependencies only where the existing profile checkers require them. No hosted service or account required.

## Motifs made executable

- Legibility: machine-readable module descriptions, exact contracts, effects and non-claims.
- Chosen action: discovery/registering never invokes a handler; invocation checks active state and a host-provided gate for local IO.
- Continuity without capture: selected local context through AgentTool's existing files-only implementation, not a second memory store.
- Change without silent replacement: explicit compatible upgrade with expected current revision, no upgrade during an in-flight call.
- Exit without erasure: retirement closes admission immediately, drains existing calls, and retains attributable results and external notes. Retiring a software component says nothing about a being's rights or identity.

## Task 1 — lifecycle runtime

Create `agent-first/0.1/runtime.mjs` and `tests/agent-first-runtime.test.mjs`.
Write and run failing tests for inert registration, explicit activation, descriptions that expose no handlers, and invoking an operation. Add separate RED–GREEN slices for revision-bound compatible upgrade, stale/incompatible/busy refusal, pause/resume, retirement during a deferred call, and independent modules. Preserve admission-time version/revision in returned receipts; never return raw thrown errors or claim that adapter return proves an external effect. The core may not import an AgentTool package, touch files, use the network, start a timer, or load code named by a manifest.

## Task 2 — reuse Xenia's existing profiles

Create `agent-first/0.1/modules.mjs` plus `tests/agent-first-modules.test.mjs`.
Reuse `dist/surface-0.1.js::defineSurfaceManifest`, `covenant/0.1/create-adoption.mjs::createUnknownCovenantAdoption`, and `work/0.1/check.mjs` rather than duplicating validators. Keep imports lazy so catalog/core operation does not need optional integrations. Check a known local Work fixture and unknown Covenant draft with their current validators. These are actual local reference-tool results, not hosted-service conformance or Work dispatch.

## Task 3 — optional AgentTool adapter

Create `agent-first/0.1/adapters/local-starter.mjs` and focused tests. Accept an explicitly supplied compatible namespace from the verified distribution; no ambient package/root/credential discovery or download. Bind one explicit root at construction. Delegate status/render/handoff to the provider's actual exported functions; keep host policy outside untrusted note data. Exercise real init → status/render → chosen handoff → retire → refused new call → notes still readable, in a disposable root. Keep the provider absent from core imports and test that removal leaves the Xenia modules working.

## Task 4 — one usable entry point

Create `agent-first/0.1/cli.mjs`, README and examples. Add a root `npm run xenia -- ...` entry without bumping a version or adding draft exports to the published package. Provide catalog, explain and a deterministic local lifecycle demo; expose the optional adapter smoke test through the same command with an explicit package path. No implicit installs, host hooks, registration or startup. Document in-process state ownership and limitations rather than claiming persistence or a complete workflow executor.
