# Xenia agent-first: connected motifs, small local pieces

**Status: repository-only development kit.** This is an optional Node host-side composition layer over existing Xenia functions—not a new normative Xenia profile, a published release, a durable workflow engine, or a model harness. It leaves the root package version, exports, Rights, Surface, Covenant and Work meanings unchanged. Most of it is written from the host's side; five commands are for the arriving side: `door plan` and `door check` look at another service's door from outside, `door rights` reads an adoption record from a local file, and `feedback new` and `feedback check` give a report a form and read one back. `session` lets a caller use the modules over JSON Lines, one request at a time, without writing a host; with `--collab-config` it also binds [the Collab adapter](adapters/agenttool-collab/README.md), which has been tested against a stand-in backend only.

## One door

From the Xenia checkout:

```sh
npm run --silent xenia -- arrive
```

`arrive` returns one bounded orientation document (under 8 KiB, tested): what this place is, the read-only commands (as argv; they change nothing here, and whether your host lets you run them is for you to decide, since this document grants no permission), the one command that sends requests, listed apart under `network` (`door check`; see [Looking at a door from outside](#looking-at-a-door-from-outside)), the core modules, the adapters listed as available but **unbound** (what each needs and its declared effects; for the Local Starter, the exact name, version, source and archive hash that `--package` must match), what the document does not establish, how to stop (nothing is running, nothing to undo) and where a report can go. It says `reply_expected: false`; `report` names the routes for a report following [AGENT-FEEDBACK.md](../../AGENT-FEEDBACK.md): a pull request, an issue, giving the note to whoever the writer answers to, if anyone, or nowhere. There is no endpoint, and no reply is promised (see [Writing a report](#writing-a-report)). It activates nothing, imports no provider and needs no build.

`node agent-first/0.1/cli.mjs arrive`, run from the repository root, is the same command without npm. That is the form on the six-line card at the top of the repository's [AGENTS.md](../../AGENTS.md), which says what the repository is, that no file is tracked under `.claude/`, what installing and `npm test` do, what reading does not establish and where a report can go. The card is static text and asks for nothing; `arrive` need not be run. [CLAUDE.md](../../CLAUDE.md) says where the card is and does not import it.

Then, as you choose:

```sh
npm run --silent xenia -- motifs
npm run --silent xenia -- motifs study list
```

Every failure from the door carries a `problem` (a kit-local shape, see Failure below) with runnable next actions (see Failure below), and `help <command>` gives one usage (words after the command name are not read, so `help door plan` gives the usage of `door`). `motifs` reads [the motif map](motifs.json) (`motifs <motif-id>` returns one card) and ends with a short `next` list; `motifs study` lists and runs the small studies (`study journey` and `study run` need the build). `catalog` lists the registered core modules and the four adapters (`bound: false`, with what each requires and, as `bound_by`, which command binds it, if any): three from metadata written in [adapter-catalog.mjs](adapter-catalog.mjs), and the fourth read from the Collab adapter's own card. `explain <id>` describes either kind, and imports no provider or adapter code; for the Collab adapter it prints the whole card. `invoke <module-id> <operation-id> --input <file>` walks the principle once from the door: in one process it registers, activates, invokes and retires a core module, with your JSON file as input, and prints a receipt (module id, version and revision; operation; declared effects; the input's byte count and sha256; outcome; the result, or on a refusal the same receipt beside the typed problem; and what the receipt does not establish). The file is read with the bounded, no-follow reader and decoded strictly (UTF-8, no byte-order mark, one JSON value, no repeated object keys, at most 1 MiB). The input rules are in `help invoke`, and a refused file says which rule it broke (missing, symbolic link, not valid UTF-8, byte-order mark, not JSON, repeated key, too large, over the limits). `explain <module-id>` ends with the `invoke` command to run. Only operations that declare no effects run this way: the Surface manifest, the Covenant draft and the Work check. An operation that declares `local-read` or `local-write` is refused before anything runs with `HOST_GATE_REQUIRED`, because this command has no host gate to consult; Local Starter notes use `context` below, and the Collab adapter is reached through `session --collab-config`. `session` keeps one process open instead: it answers requests sent as JSON lines, and has a gate of its own (see [A session](#a-session-many-requests-one-process)). `catalog` and `explain` show each operation's card (what to send, an example, what comes back and who checks the input; see [Operation cards](#operation-cards)), and mark that `state`, `revision` and `in_flight` describe a fresh runtime made for that one command, not live shared state. `demo` exercises the existing reference tools and a clearly labelled synthetic upgrade/retirement example, printing a compact step list (call, module version and revision, declared effects, outcome, size and digest of each result; lifecycle first); `demo --full` returns the complete bodies. `starter-smoke` is the pinned Local Starter check below.

Arrive, motifs, catalog and explanation need only Node 22+ and the source checkout. `door plan` and `door check` need Node 22+ and the source checkout too, and no build: they use `surface/0.1/check.mjs` beside the kit, and say `CHECKOUT_REQUIRED` when that file is not there. `feedback new` and `feedback check` need only the kit's own files; without `AGENT-FEEDBACK.md` beside the kit, `feedback check` says it could not look for the Entry ID there. `door rights` needs `covenant/0.1` beside the kit (`CHECKOUT_REQUIRED` without it) and, for its JSON Schema check, `observe/0.1` with the checkout's installed development dependencies; without those it runs the other check alone and says so. The reference demo additionally needs the normal Xenia build and the Work checker's development dependencies. For a fresh checkout, prepare once with `npm ci --ignore-scripts` and `npm run build`. Neither step installs an agent host or activates a service.

## Looking at a door from outside

`door check` is the only command in which this kit's own code sends network requests; provider code run by `context` and `starter-smoke`, and the backend process `session --collab-config` can start, are not observed by this kit, which speaks to that backend over stdio only.

Two commands look at one HTTP(S) origin. The checking is done by the unchanged Surface 0.1 checker ([`surface/0.1/check.mjs`](../../surface/0.1/check.mjs)). [door.mjs](door.mjs) adds a plan, a request budget, a fence and a short report.

```sh
npm run --silent xenia -- door plan --origin https://example.org
npm run --silent xenia -- door check --origin https://example.org --max-requests 1 --total-timeout-ms 5000
```

**`door plan` sends nothing.** It runs the checker once with a fetch that refuses every call, and prints: the target and manifest URL the checker would use; the request bounds (at least 1, at most 66, with the rule: the number depends on the manifest, which a plan has not read); the bound on decoded body bytes (56,655,360) and what that does not count; the time rule; what would be contacted (one origin, the system name resolver, GET, the two headers the checker sets, and a note that the runtime's fetch adds headers of its own: on Node 24 a loopback server also received host, connection, accept-encoding, accept-language and sec-fetch-mode); `will_not_do`; `does_not_guard`; `host_may_add`; and two ready `door check` commands, `check.first_look` (one request, the manifest) and `check.full`, each with its sizes.

**What is not guarded** is in the plan: the address a name resolves to is not inspected, so a public-looking name can lead to a private address; the service and the network path can log the sender's address; no host gate is asked; runtime proxy settings are not examined. The environment that runs the command can add those guards. This kit does not.

**The target rule.** By default a target is refused unless `normalizeTarget` from the vendored Telescope source ([`adapters/telescope/provider/dist/target.js`](adapters/telescope/provider/dist/target.js)) accepts it: HTTPS, a DNS name, port 443, not a local or reserved name. That function reads text and resolves nothing. `--allow-local-target` accepts whatever else the checker accepts (any HTTPS origin; plain HTTP on localhost, 127.x and `[::1]`), and the output records `allow_local_target: true`. A plan made with the flag also says, under `target_rule`, which default rule was set aside (`refused_by_default_as`, or null when the target needed no flag) and, when the target is an IP address, whether `isGloballyReachableAddress` in the same vendored file lists it as `not_globally_reachable` (a loopback, private, link-local, shared, documentation, multicast or reserved range) or `globally_reachable`, which says nothing about what answers there. For a name `literal_address` is null: the address it resolves to is not looked at. A check carries the same three facts as `target_rule`, the address as its word only.

A refused target is `INVALID_TARGET`, exit 2, with a `reason`. Nothing is sent, and every next action is a `door plan`: first the plan for another origin, then, when `--allow-local-target` could admit the target, the plan for it with the flag. A user name, password, path, query or fragment is never copied into the output; when the default rule refused the target, its origin (scheme, host and port) appears in the suggested `door plan` command, as the checker normalised it, so a host name or address that was typed can come back there.

**`door check` sends GET requests**: at most `--max-requests` (1 to 66), none started after `--total-timeout-ms` (100 to 120000). Both are required and neither has a default. Left out or out of range, the refusal names the flag (`required_flag_missing` with a `missing` list, `max_requests_out_of_range` or `total_timeout_ms_out_of_range`) and does not repeat what was typed. The budget is a counting function handed to the checker as its fetch, so it counts calls handed to the runtime's fetch, not requests on the wire. The runtime sends each call once, with one exception seen on Node 24: after an answer with status 421 it sends that request a second time by itself, so a service that answers 421 can receive up to twice the budget. The plan says so under `requests.on_the_wire`, and a loopback test runs that case. It is also a fence: a call that is not GET, not `redirect: "manual"`, not at the target origin, or that carries a header other than User-Agent and Accept is not sent and is counted apart (`requests.refused_by_kit_fence`). With the checker as it is today that count stays 0; the fence is there in case the checker changes.

The report, in this order: `scope`; `not_tested` (the checker's own seven lines only); `expires_at`, `observed_at`, `target`; `checker_result` (`word`, `counts`, and `covers`, which says what the word covers); `manifest` (`state` is `found_valid`, `found_invalid`, `not_found` when the manifest URL answered with a status other than 200, or `not_observed` when no response arrived or a 200 came whose body could not be read; beside it the `status` served, or null, and `means`, one fixed sentence saying what the state covers: `not_found` says only that the status was not 200, so a redirect, a refusal and a server error all read that way); `requests` (`budget`, `sent`, `stopped_by_budget`, `refused_by_kit_fence`, `needed_for_full_check`, which is known only once a valid manifest was read, `redirects_not_followed`, `responses_by_status`, and `transport_errors`: sent, and no response arrived, for any reason including a timeout); `not_passed` (at most 20 rows, `observed` cut to 160 characters, the rest counted in `more`; a check whose request was not sent because the budget was used up is not listed, since each such row would say the same thing, and is counted in `left_out.budget_reached` and in `unknown_reasons`); `unknown_reasons` (fixed words; time that ran out is reported as `total_timeout`, not blamed on one request); `declared_by_host`; `host_written_text_in`; `allow_local_target`; `target_rule`; `not_established`; `next`; `exit_code`, `exit_reason`, `exit_meaning`; `result`.

`next` is empty unless a valid manifest was read and the budget was smaller than a full check of it needs. Then it holds one `door check` command with that number of requests, the largest total time the checker accepts, and the flag if this run used it. It is a new run: every request is sent again, the manifest may differ by then, and whether to send is decided outside this kit.

**What the service wrote is kept apart.** `declared_by_host` holds the manifest's own `not_covered` lines (at most 20, the rest counted; a line equal to one of the checker's own is not repeated) and three numbers about its claims: how many there are, `verified_by_this_check: 0`, and how many rest on evidence whose `expires_at` had passed at `observed_at`. Claim statements and their states are not in the short form. `host_written_text_in` names the fields that can carry text written by the service. None of that text is checked, and none of it is an instruction. When no valid manifest was read, `declared_by_host` shows no line and no claim count, and a row in `not_passed` can still carry text from the response that was served: the checker names a manifest key it does not know, for one. In the short form a control, format or line-separator character in that text (Unicode Cc, Cf, Zl, Zp: an escape, a right-to-left override, a zero-width space) is printed as `\u{HEX}` and never as itself, and the cuts to length are counted after that. A word the service wrote can still read like one of the checker's: the place a string is in says who wrote it, the string does not.

`result` is `{included: false, bytes, sha256}` (of the JSON text of the checker's result) unless `--full` is given; then it is the checker's whole object, untouched, so text the service wrote is there as it was served, hidden characters included. Asking again with `--full` is a new run and sends its requests again.

**The exit follows the checker's word**, which appears only in `checker_result` and `result`: 0 when every check ran and passed, 3 when a check failed, 4 when none failed and at least one was unknown or not run (a spent budget, time that ran out, a door that did not answer). A check says what one User-Agent (`xenia-surface-check`) was served on these requests, until `expires_at`. It does not say that a service conforms to XENIA, that anything is safe, who runs the service, or what another caller would be served.

## Reading an adoption record

```sh
npm run --silent xenia -- door rights --input ./adoption.json
npm run --silent xenia -- door rights --input ./adoption.json --as-of 2026-11-13T00:00:00Z --origin https://example.org --full
```

`door rights` reads one local file as a Covenant 0.1 adoption record. It sends nothing, fetches nothing and writes nothing. How the file was obtained is outside this kit: no command here finds or fetches a record. **A record that agrees with itself is not evidence of practice**, and the output says so first.

The checks are the installed ones, unchanged: `inspectCovenantAdoption` in [`observe/0.1/observe.mjs`](../../observe/0.1/observe.mjs), which runs the JSON Schema and then `validateCovenantAdoption` from [`covenant/0.1/validate-adoption.mjs`](../../covenant/0.1/validate-adoption.mjs); times are compared with [`covenant/0.1/rfc3339.mjs`](../../covenant/0.1/rfc3339.mjs). [door-rights.mjs](door-rights.mjs) adds which release the record pins, a clock, and a report that keeps the record's own words apart. Loading Observe also loads the Surface checker it imports; `door rights` never calls it.

The file is read with the bounded, no-follow reader and decoded strictly: at most 2,000,000 bytes (Observe's own limit), UTF-8, no byte-order mark, one JSON value, no repeated key. A file that is not an object whose `schema_version` begins with `xenia.covenant.adoption/` is `INVALID_INPUT` with reason `not_an_adoption_record`. What `invoke xenia.covenant draft` prints is such a file: it is a receipt, with the record under `result`. To read the kit's own draft, save its `result` to a file of its own; the refusal of such a receipt says so.

**Bounds on the two checks.** Neither has one of its own. The JSON Schema check collects every issue, and when measured here its time grew with the square of an over-long array (0.3 seconds at 8,000 empty objects, 1.2 at 16,000), so a file well inside the byte limit could keep it busy for hours. The other check reads the record's `reviewed_at` again for every restriction event: a file inside the byte limit kept it busy for 108 seconds. `door rights` therefore does two things. A record that holds an array longer than the installed schema allows for any array (1,024 items, its largest `maxItems`) is not handed to the JSON Schema check: `json_schema` is `{state: "not_run", reason: "array_longer_than_schema_allows", how}`. And each run is stopped after 5 seconds, and what it had found by then is dropped. The first run is Observe's inspection, which runs the JSON Schema check and then the other check; when it is stopped, `json_schema` has `reason: "time_limit_reached"`, and which of the two it was in is not recorded. The second run is the other check by itself, made when the inspection did not finish or was not started; when it is stopped, `cross_document` is `{state: "not_run", reason: "time_limit_reached", how}`. When the other check ran, what it raises is the finding, and when it raises nothing the finding is `undetermined`, exit 4, reason `json_schema_not_run`. When it was stopped as well, the finding is `undetermined`, exit 4, reason `no_check_finished`. No finding is made from a length or from a stop. The two runs are held to 5 seconds each: of the files tried, the slowest took 10.3 seconds in all (both runs stopped), and the one that had taken 108 took 5.3. The stop is the timeout of `node:vm`, seen working on one macOS machine on Node 24. The expiry count is this command's own pass and reads each `expires_at` once; a time longer than 40 characters is counted and compared but not shown.

The report, after `schema` and `kind`, in this order: `scope`; `not_established`; `input` (`bytes`, `sha256`); `as_of` (`value`, and `source`: `flag` or `clock`); `release`; `finding`; `under_installed_rules`; `expiry`; `record_says`; `checked_by_this_command`; `exit_code`, `exit_reason`, `exit_meaning`; `issues`.

**Which release.** `release.relation` compares, as text, the two digests the record pins (`covenant.sha256` and `adoption_schema.sha256`) with those of the installed files and with one earlier snapshot written down in the command. It is `installed`; or `earlier_snapshot` (tag `npm-xenia-v0.1.0-beta.4`, commit 6419d37: the two digests equal those of `covenant/0.1` at that tag, and the record was not checked under that snapshot's rules, which this checkout does not carry); or `not_recognised` (a newer release, or bytes that are no release; the command cannot tell which). No tag is observed at run time. A test derives the earlier row again from git when the tag is in the repository, and is skipped when it is not.

**The finding** is about the file, not the host. When the record pins other bytes it is `undetermined` (exit 4) whatever the installed rules raise; what they raise is still counted under `under_installed_rules`, with a label saying it is not a finding about the record. When the record pins the installed bytes: any issue gives `inconsistent` (exit 3); no issue with the JSON Schema check not run, or with neither check finished, gives `undetermined` (exit 4); otherwise `no_inconsistency_found`. `under_installed_rules` gives, for each of the two checks, its state, its number of issues (each check keeps at most 256, so 256 means 256 or more) and a count by code, then counts by top-level field and in the ledger's duty rows. `issues` is `{included: false, count, bytes, sha256}` unless `--full` is given; then it is `{count, rows}`, each row a `check`, `code`, `path` and `message`. When the JSON Schema check was not run, `json_schema` is `{state: "not_run", reason, how}` with one of five fixed reasons: three for Observe not being there, not loading or stopping with an error, and the two bounds above. When the other check was stopped at its time limit, `cross_document` has the same three keys in place of its counts.

**A clock.** The installed rules compare evidence expiry only with the record's own `reviewed_at`, so a record whose evidence lapsed long ago raises nothing under them. `--as-of` (an RFC 3339 time; without it the clock of the machine, and `as_of.source` says which) adds the reader's time. `expiry` counts evidence whose `expires_at` is at or before `as_of`, and the rows the record gives as `pass` that rest on it. With `no_inconsistency_found`, one such row makes the exit 3; with none it is 0.

**What the exit does not carry.** The exit follows the rules above and nothing else, so a record that gives its own status as withdrawn, a clock set before the record's review, and a record that names another origin than the one given can all exit 0. Each such fact is a fixed word in `finding.also` and a sentence in `exit_reason`: `pass_rows_on_expired_evidence`; `as_of_before_reviewed_at`; `declaration_status_not_active` (draft, superseded, withdrawn, or a word outside the installed list; the status itself stays under `record_says`); and, with `--origin`, `record_names_another_origin` or `record_names_no_usable_origin`. `also` is empty when none applies.

**What the record says is kept apart, and none of it is checked.** `record_says` holds the origin the record names (parsed; only the origin is kept), its declaration status, the speaker's authority state, `reviewed_at` with the whole days from it to `as_of` (negative when the review is the later of the two) and a `relation` (`before_as_of`, `at_as_of` or `after_as_of`), and counts of outcomes, evidence states and right states. A value from the record is shown only when it is a word the installed schema lists, a timestamp of at most 40 characters, or an origin; anything else is counted as `other` or shown as null. No free text from the record is copied into the default output. With `--full`, each row carries a code and a message written by one of the two checks, and a path built from index numbers and names the installed schema defines; a test plants text and an extra key in a record and finds neither in the output. That is what was tested, not a proof about every message the JSON Schema library can write. `checked_by_this_command` is the other half: `pass_rows_checked: 0`, `signatures_verified: 0`, `evidence_fetched: 0`, `digests_recomputed: 0`, `speaker_authenticated: false`, `release_tag_observed: false`, and `relation_to_origin`, which with `--origin` says only whether the record names that origin.

So an exit of 0 covers little: the file pins the installed bytes, raised no issue under them, and no `pass` row rests on evidence expired at `as_of`. A record in which every duty passes, every digest is zero and the verifier names itself gets that 0; a test builds one. A 0 does not say that a host conforms, that the speaker has authority, that the file came from the host it names, or that anything is safe.

## Writing a report

```sh
npm run --silent xenia -- feedback new
npm run --silent xenia -- feedback new --out "$PWD/my-entry.md"
npm run --silent xenia -- feedback check --input ./my-entry.md
```

[AGENT-FEEDBACK.md](../../AGENT-FEEDBACK.md) lists eight things an entry says. [feedback.mjs](feedback.mjs) gives that list a form and reads a written entry back. Both commands are offline: they send nothing, deliver nothing and read no clock. **The notebook does not require this form**, and both outputs say `notebook_requires_this_form: false`.

**`feedback new`** prints a blank entry as `entry.text`: a dated heading, eight fields (Entry ID, Observed at, Speaker, Identity proof, Source snapshots, Network vantage, Reply path, Status) and ten sections (How I arrived and what I could inspect; Actions taken; What reduced friction; What increased friction; Observed; Inferred; Declared by the subject; Unknown; What I would keep; What I would change). The dated heading, the list of bold-labelled fields, the Entry ID form and six of the eight fields are those of the entry already in the notebook; Entry ID, Observed at and Status answer no bullet and come from that form. Network vantage and Reply path are not in that entry: they answer bullets 3 and 7. Each field that answers a bullet, and each section, quotes that bullet in an HTML comment, and a test compares the quotes with the notebook. Status is filled in as `open`. No date is filled in, because no clock is read, so the same bytes are printed every time. `parts` lists each part, the bullet it answers and whether exit 0 needs it; what a part asks for is said once, in the entry's own comment, and not again there.

With `--out <absolute-new-file>` the entry is written to that path instead of being printed. The file is created only when nothing is at the path (a link there is refused too), and the path is not copied into the output. A refusal is `INVALID_OUTPUT`, exit 1, with a `reason` (`relative_path`, `names_a_folder`, `already_exists`, `parent_missing`, `parent_not_a_directory`, `not_permitted` or `could_not_create`), and nothing is written. If writing stops after the file was made, the failure says a partial or empty file may be there and that it was not removed.

**`feedback check --input <file>`** reads one file (a regular file, not a symbolic link, at most 1 MiB, UTF-8, no byte-order mark) line by line. It is not a Markdown parser. It knows four things. A fenced code block is content, and holds no heading, field or comment. An HTML comment is not content: a `<!--` begins one when it closes on its own line, when it is at the start of a line and closes on a later one, or when it closes on a later line before any blank line, heading, list item or code fence (so a hint that an editor wrapped is still a comment). Any other `<!--` is read as text, so one quoted in a sentence does not hide the sections after it. A field is a list item beginning with a bold label and a colon, and its value runs on over the lines after it, a list under it included, up to a blank line, a heading or the next item beside it. A section is a `###` heading with what is under it. It exits 0 when it finds a dated heading (`## YYYY-MM-DD: ...`, with a date that exists), an Entry ID in the form `xenia-feedback-YYYYMMDD-label-NNN`, `Observed at` starting with a date, `Speaker`, `Status`, and at least one section with text, whichever one. It exits 3 when one of those is not found, and `finding.missing` names them. It exits 4 when the file has more than one dated heading, or one dated heading beside a level-two heading that begins with a date that does not exist (31 November, say): either way there is more than one place the entry could begin, the command does not choose, and no part is read. A heading with such a date is never read as a dated heading, and `warnings` gives its line.

The report, after `schema` and `kind`, in this order: `scope`; `not_established`; `notebook_requires_this_form`; `input` (`bytes`, `sha256`); `entry` (lines in the file, dated headings, the first and last line read as the entry, comments ignored); `finding`; `parts`; `bullets`; `warnings`; `entry_id_in_notebook`; `delivered: false`; `route`; `exit_code`, `exit_reason`, `exit_meaning`.

**The eight bullets never change the exit.** `bullets` gives, for each bullet, the labels the blank entry uses for it, each as `found` (a field or section with that label has text), `empty` (the label is there with no text) or `not_found_by_label` (`not_read` when the exit is 4). `not_found_by_label` means only that the label was not found. The 2026-07-11 entry says how it arrived under a heading of its own, `Context`, so its bullet 2 reads `not_found_by_label`; that entry exits 0, and a test cuts it from the notebook at run time to show it. A heading answers a section label when it is the label, or begins with it and goes on with something other than a letter or a digit: `What I would change first` answers `What I would change`, and `Unknowns` does not answer `Unknown`. Case is not compared.

**Nothing the entry says is repeated, and none of it is checked.** The output carries the Entry ID when it is well formed, the two dates, and the status as `open`, `resolved`, `declined`, `superseded` or `other`. `warnings` gives a kind and a line number, never the text: fourteen fixed patterns that look like a credential or a local path, applied to the first 2,000 characters of each line (a comment is scanned too), and five kinds about how the file was read: `line_not_fully_scanned`; `unclosed_comment`, a `<!--` that is not closed and was read as text; `comment_over_several_lines`, a comment that runs over more than one line and was not read as content; `repeated_label`, a field label given twice, of which the first was read; and `heading_date_does_not_exist`. The credential patterns read a secret given a name (`assigned_secret`: one of six words such as token or password, anywhere in an environment name, an ini or YAML key or a JSON key, then 12 or more characters), a URL that carries a password, a Basic or Bearer value, a private-key header, a JSON Web Token, and keys with a few well-known prefixes. The path patterns (a home or temporary folder, `~/`, a drive letter, a `\\server\share` path, a `file:` URL) look at the start of a line and, for the first two, after white space, a quote, a bracket, `=`, `:`, `*`, `|`, `<`, `>` and a comma. At most 20 rows are shown, and the rest are counted. A row is a line to look at before sharing the file; two shapes are flagged knowingly although they can hold nothing (any 20 characters after `Bearer`, and `~/` before a digit). Finding none is not a finding that there are none: a secret with no name beside it and no known prefix is not seen. `entry_id_in_notebook` says whether `AGENT-FEEDBACK.md` in this checkout already has that Entry ID: `found`, `not_found`, or `not_checked` with a reason. The notebook anywhere else is not looked at.

**Where a report goes** is one constant, printed as `route` by both commands and as `report` by `arrive`: a pull request (it needs a GitHub account, and a fork or push access; a maintainer decides, and may decline or not answer); an issue (it needs a GitHub account, and is not a notebook entry); giving the note to whoever the writer answers to, if anyone; otherwise the note stays where it was written. There is no endpoint, no command in this kit sends a report, and no reply is promised.

So an exit of 0 covers little: the file has five labelled parts and a section with text. It does not say that the entry is true, that it was delivered, that anyone will read it, or anything about who wrote it or who ran the command.

## The motifs

| Motif | The question it keeps answerable | Concrete behavior |
|---|---|---|
| **Standing** | What remains when a capability is unavailable? | Rights remain a floor. Reading what a door offers (describe, catalog, explain, motifs, help, arrive) works in every module state and after every refusal, never asks the host gate and takes no caller identity; `tests/agent-first-floor.test.mjs` runs that. The Covenant helper makes an all-unknown draft, not an active undertaking. |
| **Legibility** | Can I understand a door before using it? | Describe contracts, versions, effects and each operation's card (what to send, an example, what comes back, who checks the input) without invoking a handler. |
| **Bounded work** | What was offered, attempted, returned or observed? | Reuse Work's checker; do not execute a document merely because it records work. |
| **Continuity** | What do I choose to carry? | Use Local Starter's ordinary files, selection, freshness, budgets and guarded handoffs. |
| **Change** | Which implementation answered, and what changed? | Revision-bound replacement, declared contract/effect checks, in-flight protection and admission-time attribution. |
| **Exit** | Can this stop without taking the records with it? | Close new calls, drain admitted work, leave retained files independently readable. |

Their connection is not an automatic workflow:

```text
standing → legible choices → bounded work → chosen context
    ↑                                      ↓
    └──── exit without erasure ← attributable change
```

Understanding here is practical: each piece should explain what it does, what it needs, what it changes, what its evidence establishes, what remains unknown, and how to stop or replace it. The map is an interpretation of the linked Xenia sources, not proof of experience, authority or conformance.

## Small pieces and their ownership

- [runtime.mjs](runtime.mjs): an in-process registry for **trusted** module code. No filesystem, network, provider import, scheduler or credential lookup in the runtime. It is Node-only, not an OS sandbox.
- [schema.mjs](schema.mjs): a closed reading of JSON Schema that imports nothing: three types, ten keywords, and a refusal to compile anything else. The runtime uses it to hold an input to the schema on an operation's card; see [Operation cards](#operation-cards).
- [modules.mjs](modules.mjs): thin, lazy adapters for the existing Surface manifest builder, Covenant draft generator and in-memory Work checker. No second validator is invented: each operation's card has an input summary, an example and what it returns, and no input schema. The Surface and Covenant operations decline `invalid_input`, in the kit's words, an input that is not one JSON object (in a session, `input` left out is null) before the native function sees it.
- [adapters/local-starter.mjs](adapters/local-starter.mjs): a removable binding to an explicitly supplied AgentTool namespace and notes root. It does not implement another notes store or discover personal context.
- [provider.mjs](provider.mjs): an explicit CLI loading boundary. It checks the small distribution file set against [agenttool.lock.json](agenttool.lock.json), snapshots the checked bytes, and imports only that snapshot's core. It does not run installation scripts, MCP, the hosted-read companion or network discovery.
- [context.mjs](context.mjs): deliberate local context commands. Each process closes its module admission when the command ends; retained notes are outside the code lifecycle.
- [command-state.mjs](command-state.mjs): keeps returned operations, later verification and snapshot cleanup distinct when a composite command fails, and holds the one projection of a failure that the door prints: the `error` object, read from named fields only, and what that failure does not establish.
- [session.mjs](session.mjs): `session`. A JSON Lines door on the runtime: the first and last lines, one request at a time, a default-deny gate with a fixed allow list, a deadline that ends a wait and stops no code, receipts, and an end that says what was and was not cleaned up. The request forms and `checkRequest` are in [problems.mjs](problems.mjs), beside `checkArgv`.
- [adapters/agenttool-collab](adapters/agenttool-collab/README.md): the one binding `session` can make, with `--collab-config`. A card as data ([card.json](adapters/agenttool-collab/card.json)), the adapter ([index.mjs](adapters/agenttool-collab/index.mjs)) and a bounded JSON-RPC stdio port ([stdio.mjs](adapters/agenttool-collab/stdio.mjs)) for one AgentTool Collab journal on this device. The backend is a separate program this kit does not contain; [agenttool.lock.json](agenttool.lock.json) pins it by sha256. Tested against a stand-in backend only.
- [adapter-catalog.mjs](adapter-catalog.mjs): the adapter rows `arrive`, `catalog` and `explain` print. It imports no adapter: three rows are written there, and the fourth is read from the Collab adapter's card.
- [LINEAGE.md](LINEAGE.md): a note, not code. This project once had a second module host, `modules/0.1`, written from the same base. The note says where it is kept, that this kit supersedes it, and what was and was not carried over.
- [door.mjs](door.mjs): `door plan` and `door check`. A plan that sends nothing, then a request budget, a fence and a short report around the unchanged Surface checker. The only file here that sends requests.
- [door-rights.mjs](door-rights.mjs): `door rights`. Reads one local file with the bounded reader, runs the two installed Covenant checks on it, and reports which release it pins, what had expired at a given time, what the record says and what was not checked. No second validator is invented; it sends nothing.
- [feedback.mjs](feedback.mjs): `feedback new` and `feedback check`. A blank entry in the form `AGENT-FEEDBACK.md` describes, and a line-by-line reading of a written one with the bounded reader. It sends nothing, delivers nothing and reads no clock; `feedback new --out` creates one file and never overwrites.

Additional, separately developed adapters are present for [Skills inspection](adapters/SKILLS-INSPECTOR.md) and [Telescope recognition](adapters/telescope/README.md). They are not automatically registered or activated by this entry point, and no command imports them, with one exception: `door plan` and `door check` import one file of the vendored Telescope source, `adapters/telescope/provider/dist/target.js` (and the error classes it needs), for the text-only target rule. It does not register the Telescope adapter or call its parser. Their own guides define their provider contracts and verification scope.

## A useful path through the pieces

1. Read `motifs`, `catalog` or `explain`. Reading does not activate anything.
2. Run `demo` to construct a Surface manifest, prepare an unverified Covenant draft, and check a synthetic Work record with the existing functions. No service is contacted and no Work action is dispatched.
3. If continuity is wanted, deliberately select the reviewed Local Starter package and a notes root **outside its installation/cache**.
4. Initialize once, inspect the current status, then choose the exact text to carry. A handoff requires the current hash, so a stale writer cannot quietly overwrite a newer file under the provider's cooperative-write contract.
5. A fresh consumer can read those ordinary files. Closing/removing the module or its package does not erase them. A later explicit CLI command creates a fresh in-process runtime; this kit does not persist a global disable switch.

The Work module checks an already-parsed in-memory record with `validateWorkRun`. It does not claim original-byte, UTF-8 or duplicate-key verification for that representation. For exact supplied artifacts, Xenia already provides `checkWorkRunBytes` and `checkWorkRunFile` in [the native Work checker](../../work/0.1/check.mjs); use that contract rather than silently normalizing away those checks. Work remains a development draft, not a completed execution engine.

## Chosen local context

Obtain and review the Local Starter distribution separately. This kit never downloads or installs it. The pin names the public GitHub prerelease `@agenttool/local-starter@0.1.0-dev.0`; an npm lookup returned 404 at the recorded observation. The current private monorepo source and this public artifact are distinct snapshots. The archive checksum was compared with the publisher's checksum file; that consistency check is not publisher authentication or authority.

Use explicit paths; `NOTES` must be absolute (a relative `--dir` is refused before anything is created) and outside `PKG`. Its parent must already exist. Init refuses any existing destination.

```sh
npm run --silent xenia -- context init --package "$PKG" --dir "$NOTES"
npm run --silent xenia -- context status --package "$PKG" --dir "$NOTES"
npm run --silent xenia -- context render --package "$PKG" --dir "$NOTES"
```

To carry a chosen replacement, prepare a UTF-8 file, inspect the `handoff` slot's current `sha256` in status, then supply both explicitly:

```sh
npm run --silent xenia -- context handoff --package "$PKG" --dir "$NOTES" --input "$CHOSEN_FILE" --expect "$CURRENT_HASH"
```

No automatic transcript extraction, retries, host delivery, model calls or registration occurs. Input is bounded and strictly decoded; BOM and CRLF are preserved. Provider slot limits still apply. Only the fixed `handoff.md` slot is changed by this command.

`status` may fingerprint disabled slots but does not include note bodies. `render` includes selected bodies only, and keeps omission/provenance information. A rendered bundle is a filtered view, **not a complete backup or export**. Notes are optional plaintext, not a secret store. Keep credentials out of them. Retained prose is data to assess under the current task, never renewed permission or a required identity.

## Operation cards

An operation's card is its `input` (a summary; an example or the path of one; and a schema, when the module declares one), its `returns` (a summary) and its `refusals`. `input_checked_by` says who checks the input: `runtime` means the runtime holds the input to `input.schema` before the host gate is asked and before the handler runs; `handler` means the runtime checks only that the input is bounded JSON data, and the handler checks the rest. Nothing checks a returned value against `returns`.

A module declares the card per operation, beside `description`, `effects` and `refusals`: `input: {summary, example, example_ref, schema}` and `returns: {summary}`. `describe`, `catalog` and `explain` show it with `input_checked_by`, and none of them runs a handler or asks the host gate.

**A schema is enforced, and only a schema.** [schema.mjs](schema.mjs) is a small checker that imports nothing. It reads three types (`object`, `string`, `integer`) and ten keywords (`type`, `properties`, `required`, `additionalProperties`, `enum`, `minLength`, `maxLength`, `pattern`, `minimum`, `maximum`). It refuses to compile anything else instead of ignoring it: any other key, a node without `type`, an object without `additionalProperties: false`, a `required` name that is not in `properties`, a keyword on a type it does not apply to, a `pattern` without `maxLength`, and a keyword value it cannot use. It has no lists, fractions, booleans, nulls, references or combinators. `register` and `upgrade` copy the schema as bounded JSON data and compile it once. A schema the checker refuses, or an `example` that does not match its own schema, is `INVALID_MODULE` with a `reason` (`input_schema_not_usable` with `schema_refusal {reason, pointer}`, or `input_example_does_not_match_schema` with the miss), and nothing is registered. An `example_ref` names a file the runtime never reads, so it is not held to the schema.

`invoke` holds the frozen input snapshot to the compiled schema after the module-state and operation checks, before the host gate is asked and before the handler runs. The first miss is `INVALID_INPUT` with `reason: does_not_match_card`, `operation_started: false`, `effect_outcome: not_attempted`, and three fields: `pointer` (an RFC 6901 pointer into the input; for a missing name or an undeclared one it points at the object), `keyword` (the schema keyword that missed) and `expected` (the card's own word for it: the type, the list, the limit, the pattern, the one missing name, or the names the card declares). The pointer is built only from names the card declares, so an undeclared name and every value that was sent stay out of the output. An input that is not bounded JSON data is still refused before the card is consulted, as `INVALID_INPUT` with no `reason` from the runtime. An input that matches reaches the gate and the handler as the same frozen snapshot.

Inside one schema node the keywords are tried in a fixed order: `type`, `enum`, `maximum`, `minimum`, `maxLength`, `minLength`, `pattern`, `required`, `additionalProperties`, `properties`. The tests hold the checker and Ajv (a development dependency of this repository, which schema.mjs does not import) to the same fixture cases and to 44,000 generated values, and compare the answer, the pointer, the keyword and `expected`. Ajv runs there in strict mode and is asked to read own properties only; without that option it takes a name every object inherits, such as `toString`, to be present, and the checker never does. On those schemas and values the two agree on whether a value matches and on where the first miss is. They name the same keyword for it with one difference: on a string node that has an `enum` and also a length or pattern keyword, Ajv tries the enum before the type and calls a value that is not a string an `enum` miss, where this checker says `type`. One more difference lies outside those cases and has a test of its own: a `required` name that is the empty string is reported missing by this checker, and by Ajv 8.20.0 only when it is asked for every error. None of this shows that the checker implements JSON Schema: it reads a small part of it, and it is stricter than strict Ajv where it refuses an open object, a node without a type or a pattern without a length limit.

**What this does not do.** No returned value is held to `returns`. A `maxLength` bounds the text a pattern is tried on, not the time a badly written pattern takes on that text; a card is trusted module code, like its handler. No core operation carries a schema: the Surface and Work inputs hold lists, which the checker does not read, and a schema for the Covenant draft would be a second validator beside the native function. Their cards say `input_checked_by: handler`. One module this door can register carries schemas: `agenttool.collab`, which `session --collab-config` binds. Each of its nine cards has one and says `input_checked_by: runtime`, so in such a session an input that misses is refused before the gate is asked (one test sends one through the command line). Without that flag no command at this door reaches a schema; the enforcement is otherwise run by tests with fixture modules, and by a programmatic host that registers a module whose card carries one. The adapter rows in `catalog` carry no card; `explain agenttool.collab` prints that adapter's. A match says the input has the published shape. It says nothing about who is asking, whether the operation should run, or what it will do.

## A session: many requests, one process

```sh
npm run --silent xenia -- session
```

`invoke` walks the lifecycle once and ends. `session` keeps one process open: it reads requests as JSON lines on standard input and answers each with one JSON line on standard output, so a caller can inspect, activate, call, pause, resume and retire modules without writing a host. [session.mjs](session.mjs) is the door. The modules run on [runtime.mjs](runtime.mjs) as it is: the runtime gained no hook, hold or deadline for this, and one export, `snapshotInput`, the bounded-JSON-data rule it already held every input to. At the command line a session registers the three core modules and, when it is given `--collab-config <absolute-file>`, binds the Collab adapter (see [The Collab adapter](#the-collab-adapter)). A programmatic host calls `runSession({modules, bindings, allow, input, output})` with its own modules and gets `{done, close}` back.

**Every line is one compact JSON object, and stderr is silent.** The first line is `session_start`, at most 8192 bytes; a session whose modules cannot be listed in that does not start. It holds `what`; `modules` (id, version, state, `build` as `present`, `missing` or `not_needed`, `bound`, each operation with its declared effects and `allowed`, and for a bound module that states one, `at_end`: what its end may write without the gate being asked); `gate`; `requests` (for each method its fields, an example that names a module of this session, and what it changes); `request_fields`; `no_request_for` (`register`, `upgrade`); `responses`; `limits`; `end`; and `not_established`. Starting activates nothing and calls nothing. A session that cannot start prints one line, `session_not_started`, with `error` and `problem`, and reads nothing: a command line it does not understand, an `--allow` entry it cannot use or a `--collab-config` path that is not absolute (exit 2); a module or binding it cannot register or cannot describe within its limits, or a config file it cannot use (exit 1). `session --help` is answered as `help session`: a help document, printed like every other, and not a session line.

**A request** is one line, `{id, method, module, operation, input, deadline_ms}`. `id` is a string of 1 to 128 of `A-Z a-z 0-9 . _ : -`. A response repeats the line's `id` and `method`, each only when it matches its form, and a `module` or `operation` id that matches the id form, in `error.module` and `error.operation`; nothing else the line holds is repeated. Each of the six methods has one closed form (`REQUEST_SCHEMAS` in [problems.mjs](problems.mjs), checked by [schema.mjs](schema.mjs) through `checkRequest`), and a field the form does not name is refused.

| Method | Fields beside `id` and `method` | What it changes |
|---|---|---|
| `inspect` | `module` and `operation`, both optional | Nothing. With no module it gives the session: module states, the allow list, calls still running past their deadline, how many lines were read and answered, the request forms with the rule for each field and an example of each request, and the limits. With a module: its description, state and operations and, for a bound module, what its binding holds in memory (`look`) and what it was bound to (`bound_to`). With a module and an operation: that operation's card. |
| `activate` | `module` | A registered or paused module becomes active. |
| `invoke` | `module`, `operation`; `input` and `deadline_ms` optional | Runs one operation of an active module, once. |
| `pause` | `module` | The module, active or registered, takes no new calls until it is resumed; `resume` then makes it active. |
| `resume` | `module` | A paused module becomes active. Refused in any other state, as `INVALID_REQUEST` with reason `resume_needs_paused`. |
| `retire` | `module` | The module takes no new calls for the rest of the session and cannot be activated again in it. A bound module's binding is closed when the session ends, not at `retire`, and its answer says so (`binding_closes: at_session_end`). |

`input` is not part of the form. It is any JSON value, taken out before the form is checked and handed to the runtime, which holds it to the operation's card when the card carries a schema (see [Operation cards](#operation-cards)). Left out, it is null. No request registers or upgrades a module. The answer to `inspect` of one module is at most 8192 bytes: a module too large to describe in that refuses the start, what a binding shows as `look` is held to 2048 bytes of bounded JSON data or replaced by `{included: false, reason}`, and a binding whose `bound_to` is over 2560 bytes refuses the start.

**A response** is written for every request line that is not blank, in input order, one request at a time: `{id, line, ok, method, receipt, state}`, then `{outcome: "returned", result}` or `{error, problem}`, then `not_established`. `line` counts input lines from 1, so a response can be matched to its line even when the id could not be read (`id: null`). `state` is the named module's state afterwards, or null. The receipt names the module that answered (`id`, `version`, `contract`, `revision`) and, for a call, the `operation`, its declared `effects` and the `deadline_ms` it was given; then `request_line`, the bytes and sha256 of the line as it was received, before its newline. A receipt names an operation only when the module has it. A returned value is held to the input limits (1 MiB, 32 levels, 65536 values). One beyond them, or one that is not JSON data, is not put on the line and is not called a failure: the response says `outcome: "returned"` with `result: {included: false, reason: "not_bounded_json_data"}`. A lifecycle request answers `{from, to}`; one with nothing left to change (activating an active module, retiring a retired one) answers with the same state on both sides.

**An unusable line** is answered `INVALID_REQUEST` with a `reason` (`not_utf8`, `byte_order_mark`, `not_json`, `duplicate_key`, `line_too_long`, `operation_needs_module`, `resume_needs_paused`) or, under the reason `does_not_match_request`, with a `pointer`, a `keyword` and what the form `expected` there. The line itself is never repeated: the pointer holds only names the form declares. Lines are decoded strictly, by the decoder `invoke` uses for a file ([input-file.mjs](input-file.mjs)). A line over 1 MiB (1048576 bytes) is discarded unread and answered the same way, and the session goes on. A blank line is counted and not answered. Text after the last newline is a line. While a call is in flight the session reads ahead, and pauses its input once the lines read and not started reach 256 lines or 4 MiB (`limits.read_ahead`); a line still being read is held to its own 1 MiB besides.

**The gate is default-deny.** An operation that declares no effects is not gated. One that declares effects runs only when the allow list names it: `--allow <module-id>:<operation-id>`, entries separated by commas, fixed when the session starts. An entry that names no operation declaring effects refuses the start, and the refusal lists the operations that could be named. `allowed`, in `session_start` and in `inspect`, says what the gate will do; it grants nothing, and the gate reads nothing about the sender. The three core operations declare no effects, so without `--collab-config` `--allow` has nothing to name and every use of it is refused. With it, every operation of `agenttool.collab` declares effects and can be named. The mechanism is also run by tests with fixture modules, and by a host that passes modules of its own.

**A deadline is not a stop.** A call is given 10 seconds, unless the request sets `deadline_ms` (1 to 30000) or a bound module states another default for the operation. When that time passes the call is answered `DEADLINE_EXCEEDED`, with `operation_started: true` and `effect_outcome: unknown`. The deadline ends the wait; it does not stop the handler, which runs on, and the session goes to the next line. `inspect` lists such calls under `late`: `{line, id, module, operation, settled}`, where `settled` is `pending`, `returned`, `declined` (with `refusal_code`) or `failed`. No late result is kept. At most 32 rows are shown, those still pending first, and the rest are counted. The deadline is a timer in the same process, so a handler that keeps the process busy without yielding is answered only when it lets go.

**Inside a session a problem never gives a command line.** It is terminal, or its `next_actions` are requests for the same session: `{request, needs, why}`, where `needs: ["id"]` means the sender adds an id. A suggested request names a module only when that module is in the session. `MODULE_INACTIVE` suggests `activate` or `resume`, by the module's state, and `resume` of a module that was never activated suggests `activate`. `MODULE_RETIRED` and `SESSION_ENDING` are terminal, and so is `POLICY_BLOCKED`: the allow list is fixed, and only a session started with the operation on it runs it. A terminal problem's `not_established` names a new session, not a next action. So is `BUILD_REQUIRED`, which a call to `xenia.surface` or `xenia.work` gets before anything starts when the Xenia build is not there: no request supplies a build. The problem of a session that did not start gives command lines, because there is no session to send a request to.

**The end.** The session ends when its input ends, after every line already read is answered. SIGINT, SIGTERM or SIGHUP ends it too: the call in flight is answered, lines read but not started are answered `SESSION_ENDING` (an unusable one is still `INVALID_REQUEST`), and nothing more is read. The handlers for these are in place before the first line is written, so a signal sent as soon as that line is read is answered the same way. An output that stops taking lines (a reader that went away) closes admission at once: nothing more is read or started, the lines already read are not run, the end runs as it does for a signal with `ended_by: output_error`, and the exit is 1. Then every module is retired, each binding's `close()` is called once, and calls still running past their deadline are waited for, all within 15 seconds (`limits.end_ms`; a host may give less). The last line, `session_end`, gives `ended_by`; `lines` (`read`, `answered`, `blank`; `read` counts lines taken from the input, which can be ahead of the one being answered); each module's `state` and `in_flight`; `late`; and `cleanup` `{complete, did, did_not, left_behind}`. A handler still running by then is named in `did_not`, its module is left `retiring`, and it is cut off when the process exits. An error thrown outside any call (from a handler's timer, or a rejection nobody handles) ends the session the same way instead of ending the process at once: `ended_by` is `uncaught_error`, nothing about the error is printed, and the exit is 1. A second such error ends the process there, with no last line. The exit is 0 only when the end was complete; 1 when it was not, when the output stopped taking lines, or when a module or binding could not be registered; 2 when the command line was not understood or an `--allow` entry could not be used. A request that failed does not change the exit: its own line says how it went.

**A binding** is how a host hands a session a module that holds something: `{module, look, close, deadlines, at_end, bound_to}`. `look()` returns, from memory only, what it holds. `close()` is called once at the end of a session that started, and reports `{complete, did, did_not, left_behind}` as lists of short strings; one that throws, does not finish in time or reports something else is named in `did_not`, and nothing it said is printed. `deadlines` gives a default deadline for an operation. `at_end` is at most 8 lines saying what `close()` may write without the gate being asked; the session prints them on the module's row in `session_start` and does not check that `close()` does only that. `bound_to` is a JSON object of at most 2560 bytes saying what the binding was made with; `inspect` of the module shows it. One binding comes with this door: the Collab adapter.

### The Collab adapter

```sh
npm run --silent xenia -- explain agenttool.collab
npm run --silent xenia -- session --collab-config /absolute/path/collab.json --allow agenttool.collab:open,agenttool.collab:status
```

`session --collab-config <absolute-file>` binds one more module, `agenttool.collab`: tasks, claims, reports and an event page in one AgentTool Collab journal on this device, through a backend process that its `open` operation starts. The adapter, its card and its config keys are described in [adapters/agenttool-collab/README.md](adapters/agenttool-collab/README.md); `explain agenttool.collab` prints the card. What matters at this door:

- **Binding starts nothing.** The config file is read strictly and names every path; a file that cannot be used is one `session_not_started` line that names the rule and never repeats a value. Which bundle may run is not in the config: [agenttool.lock.json](agenttool.lock.json) pins it by sha256, and `open` compares the file with the pin before anything is copied or started. The pinned bytes are release-candidate bytes, and this kit knows no download for them.
- **Every operation declares effects**, so each runs only when `--allow` names it. The runtime holds every input to the schema on the operation's card before the gate is asked.
- **A refusal is declared only when nothing was sent**, or when the card lists the backend's code for that operation, the answer has the plain refusal shape and no key of a success is in it. The card lists 23 such pairs on six operations (`acknowledge`, `report`, `task-create`, `task-get`, `task-claim`, `task-release`), each with the places it was read at in the pinned bundle: a code is listed only when every place that raises it for that tool comes before the journal change is committed. That is a reading of the bundle's text, not an observation; the bundle was never run, and the rollback it relies on is the Bun program's. `explain agenttool.collab` shows it under `backend_refusals` and `backend_reading`; the full table is in [the record for this step](../../.hermes/verification/guest-side-step5.json). `open`, `status` and `next` pass no refusal of the backend on. Any other failed write is `OPERATION_FAILED` with an unknown effect: the binding never sends it again and sends no more writes, while `status`, `task-get` and `inspect` stay available. `inspect` of the module shows `look` (the step `open` reached, calls whose outcome is unknown, claims, the last page read) and `bound_to` (the paths, the actor, the sha256 of the config file, the pin).
- **The end writes without the gate**, and says so first: the module's row in `session_start` carries `at_end`. If `open` returned, the backend is still running and no call has an unknown or pending outcome, the binding releases the claims it still holds and ends its native session; otherwise it sends nothing. A session that ends while a call is still running past its deadline therefore sends neither, and the `DEADLINE_EXCEEDED` answer says so. The backend process is closed and the copy of the bundle removed in every case, and `session_end` lists what the binding knows it left.

Not established: that the adapter works with the real bundle (every test runs a stand-in backend written in this repository); that a refusal marked `not_applied` was observed to change nothing; that the reading of the bundle missed no place (a missed one could report a written change as not applied); that Bun or git is a particular program or version; that a deadline or a timeout stops code; anything about the caller.

**What a session does not establish**: that an operation will be admitted or will succeed; anything about who is sending requests; any effect outside the process, since effects are what a module declares; that a deadline stopped anything; that nothing else was left behind, since `left_behind` lists only what the session and its bindings know of. A session keeps nothing between processes: the next one starts with every module registered.

## Upgrade and retire deliberately

A module begins `registered`, not active or verified-ready. `activate(id)` opens admission; `pause(id)` closes it reversibly. `upgrade(id, replacement, {expectedRevision})` requires the current revision, matching declared contract and operation/effect surface, and no in-flight handler. The signature includes each operation's declared refusals, `input.summary` (what callers are told to send), `input.schema` (compared with object keys in sorted order and lists as written, so a tighter limit, a dropped `required` name or a reordered `enum` is a change) and `returns.summary`, not its example. A replacement that changes any of them is `CONTRACT_MISMATCH`. It does not prove semantic compatibility: review and test the replacement first. `upgrade` and `register` are calls a host makes; a `session` has no request for either.

Inputs are bounded JSON data. When the operation's card carries a schema, the snapshot is held to it first, and an input that does not match never reaches the gate. The host gate sees the deeply immutable snapshot delivered to the handler; it must not edit that snapshot as a form of sanitization. Prepare a deliberately changed input before invoking again. Late decisions after upgrade, pause/resume or retirement cannot start an operation under the old context.

`retire(id)` closes new admission immediately. Admitted calls drain; it neither forcibly kills JavaScript nor undoes completed effects. The retired instance cannot be silently reactivated. The caller owns result retention and any cross-process lifecycle policy. Retiring software does not retire a being's standing rights.

For the AgentTool adapter, data stays separate from package code. The CLI compares the notes root and the package root by filesystem identity (real paths, then device and inode of each ancestor), so letter case and symlinks cannot hide an overlap, and it refuses containment in either direction: notes inside the package, or the package inside the notes (`CONTEXT_ROOT_OVERLAP`). It also refuses a `TMPDIR` that resolves inside either root, because the checked copy of the package is written there (`SNAPSHOT_LOCATION_OVERLAP`). Programmatic hosts choosing their own namespace/root must enforce that separation too. Replacing code must not mean migrating or deleting notes; migrations, deletion, host hooks, MCP bindings, credentials and external copies have separate lifecycles.

A different provider artifact must be reviewed and tested before changing its pin. No `latest` lookup or automatic pin relaxation is used. Byte matching does not prove behavior, rights, source authenticity or compatibility; trusted code and a cooperative filesystem remain host assumptions.

## Failure is useful information

A failure says whether anything happened. An operation declares its refusals in advance; when its handler throws one, the result is `DECLINED` with `effect_outcome: not_applied`, the refusal code and what to do next (a stale `--expect` hash, an existing root). **`not_applied` is the module's own declaration, not something the runtime observed:** the runtime checks only that the code was declared, so a module that declines after acting would still read `not_applied`. Each module's adapter therefore declares a refusal only where its provider is known to fail before changing anything. For the Local Starter, `init` declares only `parent_unavailable` and `already_exists`, because the provider creates the directory first and may report `unsafe_root` afterwards; that, and any other `init` failure, is `OPERATION_FAILED` with an unknown outcome and points at `context status`. For `handoff`, `unsafe_root` says only that the handoff file was not replaced, because a lock or temporary file may remain. For the Collab adapter, a refusal of the backend is declared only for the codes the operation's card lists, each with the places it was read at in the pinned bundle; each such meaning says it was read, not observed, and for a claim that the backend had run git first, or may have. An undeclared handler failure stays `OPERATION_FAILED` with an unknown outcome: do not replay a mutation. `POLICY_BLOCKED` is admission, not a human's refusal. Every refusal output lists, in `not_established`, that `not_applied` is a declaration. A refusal's own words are on the output whole, as `error.refusal.meaning`; `problem.detail` repeats only as many whole sentences of them as fit in 200 characters, and then says where the whole is.

An input that does not match the schema on an operation's card is `INVALID_INPUT` with `reason: does_not_match_card`, `pointer`, `keyword` and `expected`: nothing was attempted and the host gate was not asked (see [Operation cards](#operation-cards)). The `error` object the door prints is one projection, `errorProjection` in [command-state.mjs](command-state.mjs): it reads named fields only, those four among them, so nothing else an error carries is printed.

At the CLI every failure adds `problem` `{code, detail, terminal, next_actions[{argv, why}], retryable}` (plus `valid` where the valid values are known, and `missing` where a `door` or `feedback` command was given without a flag it requires): terminal, or at least one argv to run. This is a kit-local shape. It borrows the meanings of Surface's problem (terminal or at least one next action; retryable) but it is **not** `xenia.surface.problem/0.1` and does not validate against `surface/0.1/problem.schema.json`: codes are UPPER_SNAKE and a next action is an argv, not a link. Exit 0: the command ran and reports no finding. A `door` or `feedback` body says what its 0 covers; the other commands print their result and no such statement, and `help` words the meaning of 0 that way. 1: failure or refusal. 2: the command line was not understood, names nothing that exists, or names a `door` target that was refused. 3 and 4 are set only by `door check`, `door rights` and `feedback check`: 3 ran and reports a finding, 4 ran and could not determine. A `door` or `feedback` body repeats its exit as `exit_code`, `exit_reason` and `exit_meaning`. Composite failures name the phase. Output sizes: `arrive` is bounded (8 KiB), and so are a session's first line and its answer to `inspect` of one module (8192 bytes each); a test holds `catalog` to 16384 bytes. `motifs` (the whole map, about 79 KB) and a session's answer to `inspect` of one operation (about 8.5 KB for `task-claim` of `agenttool.collab`, which lists thirteen refusals) have no stated bound. `explain agenttool.collab` prints the whole card, about 57 KB. Those two, `motifs` and `explain agenttool.collab`, are the long documents at this door. A successful `context` command no longer repeats the module's refusal tables (use `explain agenttool.local-context`).

`session` is the one command whose output is not one document: it prints JSON Lines, and its exit is 0 only when its end was complete (see [A session](#a-session-many-requests-one-process)). A response line of a session carries the same `error` projection and a `problem` of the same shape, except that a next action is `{request, needs, why}`, a request for that session, and never an argv. It adds three codes: `INVALID_REQUEST` (a line that is not a usable request), `DEADLINE_EXCEEDED` (a call that had started and did not answer in time; the effect is unknown and the handler was not stopped) and `SESSION_ENDING` (a line read and not started before the session closed).

## Verification

The default project gate is still `npm test`. It includes local module, CLI, motif and boundary regressions. Real Local Starter tests are explicit opt-ins, so a skipped real-provider test must not be called a successful integration test:

```sh
XENIA_STARTER_TEST_PACKAGE="$PKG" npm test
node tools/render-covenant.mjs --check

```

The real-package gate uses disposable synthetic roots and fresh CLI processes. It checks restart, root isolation, disabled content, stale-hash refusal with unchanged data, existing-root refusal, provider removal with retained notes, and core operation without the provider. Failure-injection cases cover FIFO rejection, code/data separation, readback failure after writes, and cleanup failure after acknowledgement. Test-fixture cleanup is distinct from retirement; it does not imply that retirement deletes data.
